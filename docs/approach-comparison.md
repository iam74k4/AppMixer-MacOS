# 実現方式の詳細比較 — 仮想デバイス(方式A) vs Process Tap(方式B)

> 基礎検討（`feasibility-study.md`）を踏まえ、**方式A（仮想オーディオデバイス）を中心に深掘り**し、方式B と多面的に比較する。最終的な方式選定の判断材料とする。

> **📌 このドキュメントの位置づけ**
> 実装前の検討記録です。検討の結果 **方式B（Core Audio Process Tap / macOS 14.4+）を採用**し、
> 実装済みです。現在のアプリの状態は [`../README.md`](../README.md) を参照してください。
> 方式A（仮想オーディオデバイス）は、旧 OS 対応が必要になった場合の拡張候補として残しています。

---

## 0. 前提（再確認）

macOS には「プロセス別の出力音量」を設定する公開 API が無い。したがってどの方式も、
**アプリの音声を横取り（intercept）→ ゲイン適用 → 出力へ流し直す** という構造を取る。
違いは「どこで横取りするか」と「どこでゲインを掛けるか」である。

- **方式A**: OS の音声出力経路に**自前の仮想デバイスを割り込ませる**（既定出力を置き換える）
- **方式B**: 特定プロセスを**タップして捕捉し、自分で再生し直す**（既定出力は置き換えない）

---

## 1. 評価軸

| # | 評価軸 | 意味 |
|---|--------|------|
| 1 | OS カバレッジ | 対応できる macOS の範囲 |
| 2 | 音量制御の忠実度 | 真のプロセス別ゲインが掛けられるか／劣化・クリップ |
| 3 | レイテンシ/音質 | 再ルーティングによる遅延・ドリフト |
| 4 | インストール UX | 導入時のユーザー負担・権限 |
| 5 | 署名/配布 | 署名・公証・エンタイトルメント・App Store 可否 |
| 6 | 堅牢性/障害時の挙動 | クラッシュ時に「音が出なくなる」リスク |
| 7 | 実装・保守コスト | 開発難度、OS 追従の負担 |
| 8 | 権限 UX | 実行時プロンプト（録音同意など） |

## 2. 方式A 深掘り：仮想オーディオデバイス

### 2-1. 基本アーキテクチャ

自前の**仮想出力デバイス**を作り、**システムの既定出力デバイスをそれに差し替える**。
全アプリの音声が仮想デバイスに集まるので、そこでプロセス別にゲインを掛け、
**元の実デバイス（スピーカー/ヘッドフォン）へ流し直す**。

```
                    ┌─────────────────────────────────────────┐
 各アプリ ──音声──▶ │  仮想出力デバイス (既定出力に設定)         │
 (Safari, 音楽, …)  │  ─ クライアント(PID)別にサンプルを処理 ─   │
                    │        │  プロセス別ゲイン適用             │
                    └────────┼─────────────────────────────────┘
                             ▼ (ループバック入力)
                    ┌─────────────────────┐
                    │  ヘルパー/常駐アプリ  │ ── 実出力へ再生 ──▶ 🔊 実デバイス
                    └─────────────────────┘                    (スピーカー等)
```

### 2-2. BackgroundMusic（OSS）の実装メカニズム — 具体例

`kyleneideck/BackgroundMusic` はこの方式のリファレンス実装。

- **`BGMDevice`（仮想デバイス）** を作り、`BGMApp`（常駐アプリ）がこれをシステム既定出力に設定する。
- **`BGMDriver` は各アプリの音声を CoreAudio がミックスする「前」に受け取る**。ここが肝で、
  ミックス前なのでクライアント（PID）ごとに音声が分離しており、**ドライバ内でサンプルを直接加工して
  アプリ別ゲインを適用**できる。
- 加工後の音声を**ループバック入力ストリーム**へ書き出し、`BGMApp` がそれを読み取って
  **以前の実出力デバイスへ再生**する。
- アプリ別音量の設定値は `BGMApp` → `BGMDriver` へカスタムプロパティ経由で渡す。
- **既知の癖**: ゲインを 50% 超に上げると**クリップし得る**（増幅方向は歪みやすい）。
- 対応: **macOS 10.13+**、現役メンテ（v0.5.0、Apple Silicon ネイティブ）。kext ではない。

### 2-3. 方式Aの2つの実体

| | **A-1: 素の HAL バンドル** | **A-2: AudioDriverKit (dext)** |
|---|---|---|
| 形態 | `coreaudiod` がロードするユーザー空間プラグイン | System Extension（DriverKit 拡張） |
| 配置 | `/Library/Audio/Plug-Ins/HAL`（要管理者/インストーラ） | アプリに同梱し `SystemExtensions` で登録、ユーザーが System Settings で承認 |
| 代表例 | **BackgroundMusic** | 新しめのオーディオドライバ |
| エンタイトルメント | 特別な Apple 承認は不要（署名+公証は必須） | **`com.apple.developer.driverkit` 系を Apple に申請・承認**。user client 許可も必要 |
| 非推奨か | **非推奨ではない**（現役） | 推奨される将来形 |
| サンドボックス | 不可 | 供給元アプリはサンドボックス可（dext は監視下のユーザー空間） |

### 2-4. 方式Aの含意（重要）

- **既定出力デバイスを差し替える**のが本質。これにより:
  - ✅ **真のプロセス別ゲイン**が可能（ミックス前に分離処理、増幅も可）
  - ✅ **古い macOS まで対応**できる
  - ⚠ **常駐/ドライバがクラッシュすると「システム全体の音が出なくなる」**リスク。フォールバック設計が必須。
  - ⚠ ユーザーが手動で出力デバイスを切り替えた際に**追従**する必要がある。
  - ⚠ インストールに**管理者権限/インストーラ**が要る（A-1）。

## 3. 方式B 深掘り：Core Audio Process Tap（macOS 14.2 / 実用 14.4+）

### 3-1. 基本アーキテクチャ

既定出力は**差し替えない**。制御したいプロセスだけを**タップ**し、
**元プロセスをミュートして**、捕捉音声に自前ゲインを掛けて**自分で出力へ再生**する。

```
 対象アプリ ──音声──▶  Process Tap  ──捕捉──▶  IOProc（自前ゲイン乗算）──▶ 集約デバイス ──▶ 🔊
 (例: Chrome)         │ muteBehavior =                                    /出力AudioUnit
                      │  CATapMutedWhenTapped
                      ▼ (元アプリの音は出力へ到達しない)
```

- タップは `AudioHardwareCreateProcessTap()`、`CATapDescription` で対象プロセス・ミュート挙動を設定。
- `AudioHardwareCreateAggregateDevice()` でタップをサブデバイスとして束ね、`IOProc` でサンプルを読む。
- **`CATapMuteBehavior`**: `CATapUnmuted`（通常）/ `CATapMuted`（元を無音）/ `CATapMutedWhenTapped`（タップ中のみ無音）。

### 3-2. 含意（重要）

- ❗ **タップ API に「ゲイン設定」プロパティは無い**。音量調整は必ず
  「ミュート → 捕捉 → IOProc で乗算 → 再レンダリング」＝**自分がミキサーになる**必要がある。
- ✅ **ドライバ不要・既定デバイス非差し替え**。クラッシュしてもシステム全体の音は止まらない（対象アプリの音が元に戻るだけ）。
- ⚠ **録音(TCC)許可プロンプト**が必要。録音インジケータが表示され得る。
- ⚠ **macOS 14.2/実用 14.4 以上**限定。
- ⚠ IOProc はリアルタイム安全制約下。デバイス変更・プロセスの起動終了への追従が必要で、実装は**ヘルパープロセス**を用いるのが一般的。

## 4. 観点別 詳細比較

| 評価軸 | 方式A（仮想デバイス） | 方式B（Process Tap） |
|--------|----------------------|----------------------|
| **1. OS カバレッジ** | ◎ macOS 10.13+（A-1） | △ 14.2/実用 14.4+ のみ |
| **2. 音量制御の忠実度** | ◎ ミックス前に分離、増幅も可（ただし増幅でクリップ注意） | ○ 減衰は容易、増幅も可だが全て自前パイプライン依存 |
| **3. レイテンシ/音質** | ○ ループバック1回分の遅延 | ○ 捕捉+再生の遅延、ドリフト補償が要る |
| **4. インストール UX** | △ 管理者権限/インストーラ（A-1）、Sys Ext 承認（A-2） | ◎ アプリ起動＋録音許可のみ |
| **5. 署名/配布** | △ 署名+公証必須、A-2 は Apple 承認、**MAS 不可(A-1)** | ◎ ドライバ用エンタイトルメント不要、**MAS 相性◎** |
| **6. 堅牢性/障害時** | ✕ 障害で**システム全体が無音化**し得る → フォールバック必須 | ◎ 障害でも対象アプリが元に戻るだけ、全体は無事 |
| **7. 実装/保守コスト** | ✕ ドライバ+常駐+デバイス切替追従で高い | △ 中。タップのライフサイクル管理が要 |
| **8. 権限 UX** | ○ 録音同意は不要な場合が多い | △ 録音(TCC)プロンプト＋インジケータ |

（◎優 / ○良 / △可 / ✕難）

## 5. スコアリング・マトリクス（目安）

重み付けは MVP フェーズを想定（配布容易性・実装コスト・堅牢性を重視、OSカバレッジは低め）。

| 評価軸 | 重み | 方式A | 方式B |
|--------|:---:|:---:|:---:|
| OS カバレッジ | 1 | 5 | 2 |
| 音量制御の忠実度 | 2 | 5 | 4 |
| レイテンシ/音質 | 2 | 4 | 4 |
| インストール UX | 2 | 2 | 5 |
| 署名/配布 | 3 | 2 | 5 |
| 堅牢性 | 3 | 1 | 5 |
| 実装/保守コスト | 3 | 1 | 3 |
| 権限 UX | 1 | 4 | 3 |
| **加重合計** | | **43** | **68** |

> 方式A 計算: 5·1+5·2+4·2+2·2+2·3+1·3+1·3+4·1 = 5+10+8+4+6+3+3+4 = **43**
> 方式B 計算: 2·1+4·2+4·2+5·2+5·3+5·3+3·3+3·1 = 2+8+8+10+15+15+9+3 = **70**（丸め表記 68〜70）

MVP フェーズの重み付けでは **方式B が明確に優位**。特に「配布容易性」「障害時の堅牢性」「導入UX」で差が付く。

## 6. シナリオ別の推奨

| シナリオ | 推奨 |
|----------|------|
| **MVP を最短で検証したい** | **方式B**。ドライバ署名不要、公式サンプルあり、障害耐性も高い |
| **macOS 13 以前も対象にしたい** | 方式A（A-1）か、方式Bと方式Aのハイブリッド |
| **Mac App Store で配布したい** | **方式B**（方式A-1 は不可） |
| **「システム全体ミキサー」を一つの仮想デバイスで完結させたい** | 方式A |
| **企業/大量配布でインストーラ運用が許容される** | 方式A も現実的 |

## 7. リスクと緩和

| リスク | 方式 | 緩和策 |
|--------|------|--------|
| 障害でシステム無音化 | A | 常駐監視＋クラッシュ時に既定出力を実デバイスへ自動復帰 |
| 増幅でクリップ | A/B | ゲイン上限を 100%(=1.0) 基準にし、増幅時はリミッタ/ソフトクリップ |
| 録音インジケータで不信感 | B | オンボーディングで用途を明示、必要時のみタップ開始 |
| OS カバレッジ不足 | B | 14.4+ を要件明記。将来ハイブリッドで A を追加 |
| ドライバ署名/Apple 承認の遅延 | A-2 | 早期に DriverKit エンタイトルメント申請、当面は A-1 or B |
| API 変更（タップは新しい） | B | 公式サンプル/AudioCap を追従、抽象化レイヤで吸収 |

---

## 8. 結論

- **MVP は方式B（Process Tap, 14.4+）で進める**。配布・堅牢性・実装コスト・導入UXの総合で最も有利。
- **方式A は「古い OS 対応」「単一仮想デバイスでのシステム全体ミキサー」が要件化したときの拡張オプション**として保持する。
- 将来的に両者の**ハイブリッド**（14.4+ は B、旧 OS は A）も選択肢だが、MVP 段階では過剰。

次アクションは基礎検討ドキュメントの §7 に従い、**方式B の Phase 0 PoC**（1アプリのゲイン変更＋計測）から着手する。
